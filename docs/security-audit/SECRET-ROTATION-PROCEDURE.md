> Audience: founder + ops. Execute in order. Tick each checkbox in your tracker.

- [ ] Identify who holds copies of the current secrets (laptops, password manager, CI envs, Railway, Vercel)
- [ ] Open Railway / Vercel dashboards in separate tabs
- [ ] Have `pbpaste`/clipboard manager OFF during this procedure

## 1. Anthropic API key

**Where to rotate**: https://console.anthropic.com → Settings → API Keys

1. Click *Create Key*, label `k2-ai-prod-2026-05-15`, copy the new value
2. Update **Railway** env var `ANTHROPIC_API_KEY` on the `ai-board` service
3. Update local `/Volumes/PARASSITA/K-AI/ai-board/.env` line 1
4. **Revoke** the old key (`sk-ant-api03-Ph1iWBR-...`) from the same console page
5. Trigger a Railway redeploy (`railway up --detach` from `ai-board/`) — verify `/healthz` returns ok
6. Check for unauthorized usage in Anthropic Usage tab over the last 30 days

## 2. OpenAI API key

**Where to rotate**: https://platform.openai.com/api-keys

1. Click *Create new secret key*, give it a name + project scope
2. Update **Railway** env var `OPENAI_API_KEY` on `ai-board`
3. Update local `.env` line 2
4. Revoke the old `sk-proj-MPgri5Dz...` key
5. Redeploy `ai-board`. Test the K-BOT endpoint from the live site: `curl -X POST https://board.k-ai.it/api/intake/kbot-chat ...`
6. Check OpenAI Usage dashboard for anomalies

## 3. Supabase service-role key (CRITICAL)

**Where to rotate**: https://app.supabase.com/project/uiuvwzrmrdqbfajguuab → Settings → API → Project API keys

> **Important order**: Supabase service role key rotation invalidates ALL clients holding it.
> Plan a 2-minute downtime window or rotate during low-traffic hours.

1. In the Supabase dashboard, scroll to *Project API keys* → next to *service_role* click **Reset** (or Reveal new key after rotation if available)
2. Copy the new `sb_secret_...` value
3. Update **Railway** env var `SUPABASE_SERVICE_KEY` on `ai-board`
4. **Fix the misconfiguration** — `NEXT_PUBLIC_SUPABASE_ANON_KEY` currently holds the OLD service key. Replace it with the **publishable / anon** key (separate value, starts with `sb_publishable_...`). Find it on the same Supabase API page under *Project API keys* → *anon public*.
5. Update local `.env`:
   - line 11 `SUPABASE_SERVICE_KEY=<new service key>`
   - line 13 `NEXT_PUBLIC_SUPABASE_ANON_KEY=<publishable key, NOT service>`
6. Redeploy `ai-board`. Watch logs for `Errore lettura sessione board` or Supabase 401s for 5 minutes.
7. Check Supabase logs (Database → Logs → API) for unexpected requests using the old key prior to revocation timestamp.

## 4. Telegram bot token

**Where to rotate**: open Telegram, chat with `@BotFather`

1. `/mybots` → select `k2_ai_board_bot` (or your bot name) → API Token → **Revoke current token**
2. BotFather replies with a new token
3. Update **Railway** env var `TELEGRAM_BOT_TOKEN`
4. Update local `.env` line 15
5. Redeploy `ai-board`. Verify with `/start` from the founder Telegram account.
6. If running in webhook mode, also generate a new `TELEGRAM_WEBHOOK_SECRET`:
   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(32))"
   ```
   Set this in Railway env and local `.env`. The app will pass it to `set_webhook` on next start and validate the `X-Telegram-Bot-Api-Secret-Token` header on every webhook call.

## 5. Resend API key

**Where to rotate**: https://resend.com/api-keys

1. Create a new key scoped to *Sending access* on domain `k2-ai.it`
2. Update Railway env `RESEND_API_KEY` on `ai-board`
3. Update local `.env` line 22
4. **Delete** the old key in Resend dashboard
5. Redeploy. Test contact form submission end-to-end (a real submission triggers a confirmation email).

## 6. Board admin password

**Where to rotate**: in your password manager (1Password / Bitwarden), then env vars

Constraints:
- ≥ 20 characters (was 10)
- No date/birthday/personal pattern (was `02122002_Lu!`)
- Mix of upper/lower/digit/symbol
- Random, generated by the password manager

1. Generate the new password in 1Password/Bitwarden. Save it under entry *K2-AI Board admin*.
2. Update Railway env `BOARD_PASSWORD` on `ai-board`
3. Update local `.env` line 35
4. Redeploy `ai-board`. Log into `https://board.k-ai.it/login` with the new password.

> **Note**: `BOARD_PASSWORD` is currently used both as login secret AND as HMAC key for emergency-session tokens (`core/board_auth.py:60`). Rotating the password invalidates all active env-token sessions — users will be re-prompted to log in. This is acceptable.

## 7. Newsletter publish path token (kai-website — committed to git)

**Where to rotate**: `kai-website/.env` AND search git history

> This token was committed to the public `kai-website` repo at some point and may still be in `git log`. **Must** rotate regardless of current state.

1. Generate a new token: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`
2. Update **Vercel** env var `NEWSLETTER_PUBLISH_TOKEN` (or the equivalent var name used by the kai-website function) on the `kai-website` Vercel project
3. Update local `kai-website/.env` (if present locally, do not commit)
4. Update any GitHub Actions / Railway / external integrations that hit `/api/newsletter/publish`
5. Trigger a Vercel redeploy of `kai-website`
6. Verify by calling the endpoint with the new token; confirm 401 with the old token

- Add `BOARD_SESSION_SECRET` as a dedicated HMAC key separate from `BOARD_PASSWORD` (so future password rotations don't churn sessions)
- Set up Supabase RLS (see migration `db/migrations/005_enable_rls.sql`)
- Enable MFA on Anthropic, OpenAI, Supabase, Vercel, Railway, Resend, GitHub admin accounts
